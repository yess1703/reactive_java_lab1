# Музыкальный стриминговый сервис

Три лабораторные на одной модели треков. Первая считает статистику циклом и последовательными стримами. Вторая добавляет задержку чтения страны исполнителя, параллельный стрим, свой `ForkJoinPool` и JMH. Третья использует RxJava Observable и Flowable с backpressure.

## Что делает программа

1. Создаёт исполнителей, альбомы и треки с корректными случайными характеристиками.
2. Считает количество треков, общую и среднюю длительность, сумму прослушиваний и количество треков каждого жанра.
3. Выполняет расчёт циклом `for`, стандартными коллекторами Stream API и собственным коллектором.
4. Проверяет совпадение результатов и измеряет время для **5 000, 50 000 и 250 000 треков**.

## Запуск

Нужны **JDK 17 или новее** и PowerShell. В терминале из папки проекта:

```powershell
.\run.ps1
```

Скрипт компилирует проект, запускает проверки и замеры. JDK берётся из `JAVA_HOME` или папки пользователя `.jdks`. Путь можно указать вручную:

```powershell
.\run.ps1 -JdkPath "C:\path\to\jdk"
```

В IntelliJ IDEA выберите JDK 17+ и запустите `ru.music.Main`. Для отдельного запуска проверок — `ru.music.StatisticsTest`.

Вторая лабораторная запускается отдельно. Скрипт один раз скачивает JMH в `lib`, прогоняет проверки и пишет результаты JMH:

```powershell
.\benchmark.ps1
```

Проверки без замеров: `.\benchmark.ps1 -SkipBenchmark`.

## Результаты

Время измеряется через `System.nanoTime()`: 10 прогревочных запусков и 7 замеров для каждого способа. Генерация данных и вывод текста в замер не входят. Все три способа используют последовательную обработку одной коллекции.

- `results/summary.txt` — статистика и таблицы времени на русском.
- `results/measurements.csv` — все 63 замера с началом, концом и длительностью в наносекундах.

В таблицах **медиана** — четвёртый из семи замеров, отсортированных по времени; **минимум** — самый быстрый замер. Чем меньше время, тем быстрее расчёт. При повторном запуске время может измениться, а файлы результатов перезаписываются.

## Вторая лабораторная

`Artist.country(long delayMillis)` ждёт указанное число миллисекунд и возвращает ту же страну. Ноль означает обычное чтение. Этот метод вызывается, когда статистика группирует треки по странам. Отрицательная задержка отклоняется.

Последовательный вариант — `stream().collect(...)` с `EnumMap` и `TreeMap`. Параллельный — `parallelStream()` с одним общим накопителем: счётчики `LongAdder`, жанры в `ConcurrentHashMap`, страны в `ConcurrentSkipListMap`. Так карты не ломаются, когда несколько потоков обновляют их одновременно. Задержка выполняется до записи в карты, поэтому ожидание идёт параллельно, а не под общей блокировкой.

Свой пул — `ForkJoinPool` на все процессоры машины. Задача делит диапазон треков пополам, пока фрагмент больше порога, и считает фрагмент тем же последовательным накопителем. При задержке порог маленький, чтобы ждать могли сразу несколько потоков. Без задержки фрагменты крупнее: накладные расходы на задачи не съедают сам подсчёт.

JMH измеряет среднее время одного сбора. Для задержки 0 мс размеры начинаются с 1 000, 5 000, 15 000, 50 000, 100 000 и 250 000 треков. Для задержки 1 мс — с 1, 2, 4, 8, 16, 32, 64 и 128. Если на этом диапазоне преимущество не переходит от одного стрима к другому, прогон добавляет соседний размер. Точка равенства — линейная интерполяция между двумя соседними размерами, где более быстрый способ меняется. Если интервалы погрешности JMH пересекаются, отчёт перечисляет эти размеры отдельной строкой.

- `results/lab2-summary.txt` — таблицы и найденное число треков.
- `results/lab2-measurements.csv` — средние JMH и погрешность.

## Третья лабораторная — RxJava

Запуск из PowerShell (JDK 17+, при первом запуске нужен интернет для Maven Central):

```powershell
.\lab3.ps1                 # проверки, большой Flowable, JMH для 500 и 2500 треков
.\lab3.ps1 -SkipBenchmark  # проверки и большой Flowable без длительного JMH
```

Путь к JDK можно указать через `-JdkPath`. Подключены RxJava **3.1.10** и Reactive Streams **1.0.4**. Для IntelliJ IDEA нужно обновить Maven-проект после изменения `pom.xml`. Все тесты здесь запускаемые классы с `main`, а не JUnit; скрипты запускают их явно. Старые команды `run.ps1` и `benchmark.ps1` продолжают запускать ЛР1 и ЛР2.

### Observable и Scheduler

`ReactiveStatistics.observable(tracks, delayMillis)` возвращает холодный `Single<MusicStatistics>`, построенный из Observable. Работа начинается при подписке. `Observable.range` создаёт номера независимых частей списка. Каждая часть обрабатывается в `Observable.fromCallable(...).subscribeOn(scheduler)`, а `flatMap` объединяет результаты. Внутри задачи треки обходятся с шагом, равным числу частей, и накапливаются в отдельном `Accumulator`. Объединение сериализовано оператором RxJava: общие конкурентные карты не нужны.

Scheduler создан через `Schedulers.from` над собственным фиксированным пулом. Одновременно существует не больше `workers` задач, а не отдельный поток на каждый трек. Число потоков по умолчанию — `min(128, max(32, CPU * 4))`; конструктор позволяет задать его явно. Дополнительные потоки позволяют перекрывать блокирующее ожидание в `Artist.country(1)`. `close()` освобождает пул. Список входных треков нельзя изменять до завершения подписки.

Observable сам не поддерживает backpressure. Здесь размер входного списка известен, а количество задач ограничено. Для непрерывной генерации большого числа объектов используется другой путь — Flowable.

### Flowable и собственный Subscriber

`ReactiveTrackSource.generate(count, seed, scheduler)` использует `Flowable.generate` и создаёт **один трек на один запрошенный элемент**. `MusicGenerator.nextTrack` выделен из прежнего генератора списков; сами характеристики треков и порядок случайных вызовов сохранены. Состояние генератора создаётся отдельно для каждой подписки. `subscribeOn` переносит генерацию на Scheduler; предварительного списка из миллиона треков нет.

`StatisticsSubscriber` реализует `FlowableSubscriber<Track>` (расширение Reactive Streams Subscriber):

- `onSubscribe` запрашивает первую порцию через `request(batchSize)`;
- `onNext` добавляет трек в статистику и после обработки всей порции запрашивает следующую;
- `onComplete` отдаёт готовую статистику;
- `onError` передаёт ошибку ожидающему коду;
- `close` отменяет подписку; timeout и прерывание в `await` тоже останавливают источник.

В `Lab3Main` генератор и обработчик работают на **разных однопоточных Scheduler**. `observeOn(..., false, 128)` ограничивает предварительную выборку, Subscriber запрашивает по 256 элементов. Регулируется количество разрешённых элементов, а не фиксированная частота в элементах/секунду. Медленный обработчик ограничивает дальнейшую генерацию; не используются `BUFFER` с неограниченным накоплением, пропуск элементов или `request(Long.MAX_VALUE)`.

В этом сценарии нет искусственных задержек: статистика вызывает `country(0)`, генератор не вызывает `sleep`. «Без задержек» означает отсутствие добавленного ожидания и зависаний; обработка и сборка мусора всё равно занимают время.

### Проверки и результаты

`ReactiveStatisticsTest` проверяет совпадение статистики, пустые и одноэлементные источники, 500/2500 треков с задержкой и без, повторные подписки Observable, фактическую конкурентность задач, отсутствие генерации без спроса, точное выполнение `request(3)`, отмену, порции Subscriber, ошибки и таймаут.

`Lab3Main` дополнительно обрабатывает 250 000 и 1 000 000 треков в отдельной JVM с **`-Xmx128m`** и ограничением времени 60 секунд на сценарий. Проверяются число созданных/учтённых элементов, суммы распределений по странам и жанрам и максимум созданных, но ещё не обработанных треков (не более 129 с учётом выполняющегося callback). В сохранённом прогоне максимум составил 128; оба сценария прошли. Эти длительности — проверка работоспособности, не JMH: миллион может обработаться быстрее первого меньшего сценария после прогрева JVM.

`ReactiveStatisticsBenchmark` сравнивает неизменённый `StatisticsCalculator.parallel` из ЛР2 с Observable на одинаковых входных списках, при одинаковой задержке **1 мс на каждый трек**. Создание данных и пула вынесено в `@Setup(Level.Trial)`. В Observable-бенчмарке `blockingGet()` входит в замер: учитывается полный расчёт, а не только постановка задач. Перед замерами результаты обоих методов сравниваются с последовательным эталоном.

Условия JMH: 2 forks, 3 прогревочные итерации по 500 мс, 5 измерительных по 1 с, один вызывающий JMH-поток, среднее время в мс/операцию. Сохранённый запуск: JDK 26.0.2.1, 8 доступных процессоров, commonPool parallelism 7, Observable workers 32.

| Треков | parallelStream, мс/op | Observable, мс/op | Ускорение parallel / Observable |
|---:|---:|---:|---:|
| 500 | 117,999 ± 5,080 | 31,418 ± 1,144 | 3,756 |
| 2500 | 571,482 ± 86,898 | 142,829 ± 9,285 | 4,001 |

На обоих размерах условие по производительности выполнено. Сравниваются **разные конфигурации пулов**: выигрыш связан в том числе с большим числом одновременно ожидающих задач, а не с гарантированной скоростью RxJava относительно Stream API. Результат зависит от машины и нагрузки. `Lab3BenchmarkMain` проверяет отношение средних и завершает запуск с ошибкой, если на каком-либо размере Observable медленнее; погрешности сохраняются для отдельной оценки надёжности вывода.

Файлы результатов (новый запуск перезаписывает только соответствующие файлы ЛР3):

- `results/lab3-summary.txt` — сравнение средних и конфигурация запуска;
- `results/lab3-jmh.json` — исходный результат JMH, включая отдельные измерения;
- `results/lab3-jmh-console.txt` — консольный лог выполненного прогона;
- `results/lab3-flowable-summary.txt` — проверка большого потока при ограниченной памяти.
